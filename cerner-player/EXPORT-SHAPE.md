# What a Cerner export looks like

The shape of each artifact the builder's **Export → Cerner** target produces,
and where every piece goes. Procedure lives in `DEPLOYMENT.md`; platform
behaviour in `PLATFORM-NOTES.md`; the server-side vocabulary in
`../cerner-ccl/PAYLOAD-REFERENCE.md`. This document is only about shape.

Everything here is generated by `lib/cerner-export` from the form model, and
the samples under `cerner/` are built with the same helpers the player uses
on the wire (`buildParameterString`, `toAsciiJson` with `forceF8Ids`), so
what the export shows is what PowerChart receives. The in-app **Preview →
Cerner Files** view and **Details…** modal render the identical artifact.

## The two halves of a deployed MPage

A deployed form is two folders that meet on the content server:

```
custom_mpage_content/
└── webforms-<formId>/            ← the PLAYER (built once, per player version)
    ├── index.html                   WEBFORMS_PLAYER_CONFIG baked in
    ├── assets/…                     main.js, main.css, babel.js (lazy)
    └── forms/
        └── <formId>/             ← the FORM (exported per form, from the builder)
            ├── index.jsx            MOIS runtime source
            ├── Identity.json        MOIS identity
            └── document.json        form definition (Terra target reads this)
```

The player is built by `pnpm --filter @webforms/cerner-player export:mpage`
and deployed once. The builder's export produces the **form half** plus the
config and documentation to drop it in. That split is deliberate and matches
the direction agreed with the interface team: one generic host that plays
form definitions, not one MPage per form — a new form never needs the apps
team to rebuild or re-register anything.

## Channel A — full-page MPage (`mode: "mpage"`)

ZIP: `webforms-<formId>.cerner-mpage.zip`, containing `webforms-<formId>/`:

| Path | What it is |
|---|---|
| `forms/<formId>/index.jsx` | The generated MOIS form — the same source a MOIS ZIP carries, produced by the same pipeline after the same compatibility check. Absent when the form fails MOIS compatibility and the Terra target is selected. |
| `forms/<formId>/Identity.json` | MOIS identity: name, title, type, versions, bundled components. |
| `forms/<formId>/document.json` | `{ schemaVersion, name, title, fields }` — the builder's field model, which the Terra target renders directly. |
| `player.config.json` | `{ formId, theme: "cerner", render?: "terra" }` — the object the CLI bakes into `index.html` as `window.WEBFORMS_PLAYER_CONFIG`. |
| `DEPLOY.md` | The prefmaint / static-content procedure with this form's ids substituted. |
| `cerner/file-document.request.json` | The request the player sends on "File to chart" (below). |
| `cerner/file-document.reply.sample.json` | The reply shape the player parses. |
| `cerner/poll.request.json` | The request the Tier-2 launch-out shell polls with until a submission marker appears. |
| `cerner/filed-document.sample.html` | The exact note body that will be filed, with sample answers. |
| `cerner/filed-document.labelled.sample.html` | The same rows keyed by label — **not** what is filed today; see gaps. |
| `cerner/PREREQUISITES.md` | The once-per-domain CCL, tables, whitelist entries and code values this form depends on. |
| `manifest.json` | Machine-readable summary: hosting, chart reads, the write path, server-side status, Terra compatibility, review issues. |

### How the form reaches PowerChart

`prefmaint` adds a **Discern Report** tab whose `REPORT_NAME` is

```
<url>$DM_INFO:CONTENT_SERVICE_URL$/custom_mpage_content/webforms-<formId>/index.html
```

with `WEB_BROWSER_SELECTION = 1-Edge Chromium` on that tab. PowerChart loads
the page as a **top-level document in Edge WebView2**. No CCL redirect
script is involved.

### How patient context arrives

The first CCL call the player makes carries PowerChart's macros in the
positional prompt — `$PAT_PersonId$` / `$VIS_EncntrId$` — which the host
substitutes at send time. The entry script echoes the resolved `chartId`
back, and the player adopts it. Nothing is passed on the URL.

### The request that files the form

One `XMLCclRequest` round-trip. Two parts:

**Positional prompt** (the `send()` argument):

```
^MINE^,$PAT_PersonId$,$VIS_EncntrId$,0,0,^{"mode":"CHART","hexMode":false}^
```

Slots: `OUTDEV, PERSONID, ENCNTRID, DEBUG_IND, INSTANCE, ^CONFIG^`. The
instance index (slot 5) is echoed back so a pooled set of request objects
can demultiplex replies.

**Request blob** (`setBlobIn`), ASCII JSON, whole-number `*Id`/`*Cd` values
emitted as `0.0`-style floats so CCL types them `f8`:

```jsonc
{ "payload": {
    "patientSource": [{ "personId": 0.0, "encntrId": 0.0 }],
    "customScript": { "script": [
      { "name": "nh_wf_write_document:group1", "id": "file-document", "run": "post",
        "parameters": {
          "eventKey":   "WEBFORMDOC",        // code set 72 display key
          "title":      "<form name>",
          "document":   "<h2>…</h2><table>…</table>",
          "noteFormat": "AH"                 // code set 23: authenticated HTML
        } },
      { "name": "nh_wf_form_store:group1", "id": "submission-marker", "run": "post",
        "parameters": { "action": "w", "data": [{
          "refName": "<formId>", "refTask": "submission",
          "description": "<form name>",
          "parentEntityId": 0.0, "parentEntityName": "ENCOUNTER",
          "refText": "{\"filedAt\":\"…\"}"
        }] } }
    ] }
} }
```

The document write goes through Cerner's supported `mmf_publish_ce` API —
never a direct `clinical_event` insert. The acting user is always the
server's `REQINFO->UPDT_ID`; a user id in the payload is ignored by design.
The second script writes the marker the launch-out shell polls for, in the
same envelope, so there is exactly one write moment.

### The reply

```jsonc
{ "runStats": { "status": "S", "prsnlId": …, "prsnlName": "…" },
  "chartId":  { "personId": …, "encntrId": …, "nameFullFormatted": "…" },
  "errors":   [],
  "customPost": [
    { "id": "file-document",    "data": { "status": "success", "statusValue": 1, "parentEventId": … } },
    { "id": "submission-marker", "data": { "rows": [{ "refText": "…" }] } }
  ] }
```

`errors[]` non-empty, or `data.status !== "success"`, means nothing was
filed. Control characters `0x00–0x1F` are stripped before parsing; a `%PDF`
body means the CCL program does not exist in the domain; HTTP 492 is a
non-fatal success.

### What lands in the chart

A clinical document under event key `WEBFORMDOC` (configurable) in
authenticated-HTML format. The body is, today, exactly:

```html
<h2>Newborn Record</h2>
<table>
  <tr><td><b>mother_name</b></td><td>Sample Mother's Full Name</td></tr>
  <tr><td><b>delivery_date</b></td><td>2026-01-15</td></tr>
  …
</table>
```

That is a **note**, not discrete data: no DTAs, nothing chartable in iView
or results review. Producing discrete results is Channel C's job.

### Known gaps, recorded in the manifest

- Rows are keyed by **field id**, not label. `filed-document.labelled.sample.html`
  shows the readable form this should move to; the player's
  `formDataToNoteHtml` is where it changes.
- The server-side CCL is written clean-room and **not yet compiled in any
  domain** — five `!! SITE REVIEW` markers, the blocking one being the
  `mmf_publish_ce` request-record layout. Until it compiles, the form renders
  but "File to chart" returns an error and writes nothing.
- The Terra render target is exercised in the player but the deployable
  player build does not yet ship the Terra target by default; `render:
  "terra"` in `player.config.json` selects it once it does.

## Channel A′ — Workflow component (`mode: "component"`)

Same form folder, different host. ZIP root is `webforms-player/` — the
folder name doubles as the custom-element tag, so it must not change.

| Path | What it is |
|---|---|
| `forms/<formId>/…` | Identical to Channel A. |
| `placement.html` | The markup Cerner's component framework renders: `<webforms-player title="…" path="{url}" form-id="<formId>" theme="cerner" [render="terra"]>`. |
| `REGISTER.md` | Per-form steps; the once-per-domain component registration is in `DEPLOYMENT.md` §B. |
| `cerner/…`, `manifest.json` | Identical to Channel A. |

Patient context arrives differently: from the **host page's query string**
(`pId` / `eId` / `uId`), which the element reads. The write path is the same
CCL round-trip. The host page's CSS can reach the form (light DOM), and
global CSS from the form is treated as radioactive by the surrounding page —
`<TerraBase>` is scoped for that reason.

## Channel B — SMART on FHIR (`mode: "smart"`)

ZIP: `webforms-<formId>-smart.cerner-smart.zip`. This is registration and
payload material for the player's existing SMART app, not a new app.

| Path | What it is |
|---|---|
| `smart/launch.json` | Client id placeholder, launch/redirect URLs, the scope string the Ignite registration must grant, FHIR version 4.0.1. |
| `smart/questionnaire-response.sample.json` | A `QuestionnaireResponse` shaped the way the player builds one: `status: completed`, `item[]` keyed by field id with typed answers (`valueDecimal`, `valueDate`, `valueBoolean`, `valueString`), and `subject` / `encounter` / `author` references that `hydrateFhirResource` fills from the launch token at runtime. |
| `forms/<formId>/document.json` | The form definition the app plays. |
| `README.md`, `manifest.json` | |

Context arrives via EHR launch (`?iss=&launch=`); reads are FHIR R4 with no
CCL and no compile cycle. Verified end to end against the SMART Health IT
reference server only; which write operations Cerner Ignite supports per
resource still has to be confirmed against the R4 catalogue.

## Channel C — PowerForm build spec (`mode: "powerform"`)

ZIP: `<formId>.cerner-powerform.zip`.

| Path | What it is |
|---|---|
| `powerform-build-spec.json` | Sections and controls mapped from the form with input families, task-assay and event-code placeholders marked `unresolved`, and a compatibility report. Schema `cerner-powerform-build-spec/v0`. |
| `powerform-build-worksheet.md` | The same, as an analyst worksheet. |
| `manifest.json` | |

The only channel that yields chartable discrete results, and the only one
with nothing runnable in it: an analyst builds the PowerForm in DCP Tools /
DTA Wizard from the worksheet, resolving code values in the target domain.
Experimental and untested in Cerner.

## `manifest.json`

Every channel carries one. Fields:

```jsonc
{ "schemaVersion": "cerner-export/v1",
  "generatedAt": "…",
  "mode": "mpage | component | smart | powerform",
  "renderTarget": "mois | terra | null",
  "form": { "id", "name", "fieldCount", "answerFieldCount" },
  "hosting": { "kind", "appName", "entry", "contextSource", "browser" },
  "chartReads": [ "…what this channel can read…" ],
  "chartWrite": { "channel", "script?", "api?", "eventKey?", "noteFormat?", "documentShape?", "resource?" },
  "serverSide": { "entryScript?", "scripts": [], "tables": [], "status" },
  "terra?": { "supportedCount", "unsupportedCount", "controls": [], "unsupported": [] },
  "files": [ "…every path in the export…" ],
  "issues": [ { "severity": "error | warning | info", "message", "fieldId?" } ] }
```

`issues` is the honest ledger: an `error` blocks the download; `warning`
and `info` ship with it. The CCL-not-compiled warning and the id-keyed-rows
note are always present on Channels A and A′ until those change.
